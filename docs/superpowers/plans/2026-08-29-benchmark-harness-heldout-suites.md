# Benchmark Lab Harness + Held-Out Suites Implementation Plan

> **Execution:** use `superpowers:executing-plans` and `superpowers:test-driven-development` task-by-task. No production implementation may precede an observed RED for that task.

**Goal:** Complete Foundation Convergence Wave 4 by connecting the certified typed Benchmark Lab kernel to the existing schema-3 A/B harness, making explicit Habitat ablations executable under the same scaffold, and establishing deterministic held-out/mutated suites covering all eleven benchmark classes without leaking evaluator oracles into the agent workspace.

**Architecture:** Keep `benchmarks/agent_ab_harness.py` as the existing wire/CLI entrypoint. Legacy schema-3 usage remains compatible, including plumbing runs with fewer than three repetitions. A new opt-in strong-evidence path constructs `BenchmarkSpec` / `ExperimentPlan`, executes the exact planned conditions, records `RecordedBenchmarkResult` receipts, admits them through `ExperimentEvidence`, and serializes raw pair-level comparisons. Held-out tasks are generated into isolated temporary source trees from fixture identifiers; evaluator-only mutation/oracle state is never copied into those trees or included in agent payloads.

**References:**
- `docs/design/FOUNDATION-CONVERGENCE.md` §7, Wave 4, exit criterion 7
- `benchmarks/AGENT-AB-BENCHMARK-CONTRACT.md`
- `habitat/benchmarking/model.py`
- `habitat/benchmarking/experiment.py`

## Invariants

- Preserve existing alpha.19 protocol/MCP/workspace/store behavior.
- Preserve existing schema-3 harness CLI/report behavior when strong mode is not requested.
- Strong evidence requires at least three unique repetitions/seeds and an independent evaluator.
- Filesystem and Habitat conditions use the same declared model/scaffold identity.
- Every Habitat ablation uses the **same Habitat command/scaffold** as Habitat ON; only the explicit ablation configuration changes.
- No hidden evaluator configuration, mutation seed, or oracle may appear in an agent payload or generated agent repository.
- Same task repetition uses the same generated source snapshot across all conditions.
- A strong result is admitted only by the typed fail-closed receipt layer; dictionary similarity is not sufficient.
- Missing metrics remain unavailable (`None`), never coerced to measured zero in the strong-evidence section.
- One-time ingest, warm reconcile, and per-task interaction costs remain separately represented.
- Raw run/evaluator receipts and per-pair distributions are preserved. The strong section must not emit a single superiority headline/mean that hides tails.
- No model-quality or Habitat-superiority claim is generated by this implementation.

## Task 1 — Typed Strong Suite Contract and Held-Out Fixture Boundary

**Files:**
- Create: `habitat/benchmarking/suite.py`
- Modify: `habitat/benchmarking/__init__.py`

**Domain contracts:**

```python
@dataclass(frozen=True)
class HeldOutTask:
    task_id: str
    benchmark_class: BenchmarkClass
    prompt: str
    fixture_id: str
    task_fingerprint: str
    repository_revision: str
    budget: tuple[tuple[str, int | float], ...] = ()


@dataclass(frozen=True)
class HeldOutSuite:
    suite_id: str
    tasks: tuple[HeldOutTask, ...]

    @property
    def class_coverage(self) -> tuple[BenchmarkClass, ...]: ...
```

The domain layer stores only agent-safe task metadata. Evaluator-only oracle/mutation state remains runner-side and MUST NOT be a field on `HeldOutTask`.

### Step 1 — RED tests

- normalized immutable numeric budget entries; booleans/non-finite/negative values rejected;
- deterministic `class_coverage` in canonical `BENCHMARK_CLASSES` order;
- optional `require_complete_taxonomy()` rejects a suite missing any of the eleven classes and reports exact missing classes.

### Step 2 — Observe RED

### Step 3 — GREEN implementation

Use frozen dataclasses and existing validation/fingerprint conventions. Do not add a third-party schema package.

**Fixture boundary:**

```python
@dataclass(frozen=True)
class MaterializedFixture:
    fixture_id: str
    repository_revision: str
    task_fingerprint: str
    evaluator_payload: dict[str, object]


def materialize_fixture(
    fixture_id: str,
    destination: Path,
    mutation_nonce: str,
) -> MaterializedFixture: ...
```

The destination contains only agent-visible source/project files. `evaluator_payload` remains in the harness process and is supplied only to the evaluator command.

### Required fixture taxonomy

The committed catalog must contain at least one deterministic fixture definition for every class:
1. retrieval/orientation
2. semantic navigation
3. refactor/rename
4. debugging
5. multi-file implementation
6. test selection
7. runtime diagnosis
8. UI tasks
9. multi-agent invalidation
10. adversarial/authority tests
11. large repository scaling

“Large repository scaling” must be generated to a declared non-trivial scale (file/symbol counts asserted in tests) rather than relabeling a tiny fixture.

### Step 1 — RED tests

Require:
- catalog covers all eleven classes exactly/at least once;
- same fixture + mutation nonce produces byte-identical source tree and same fingerprints;
- different nonce changes mutation-bound fingerprints/source where the fixture is mutable;
- evaluator payload is returned out-of-band and no oracle keys/expected answer/mutation nonce appear in generated files;
- materialization refuses path traversal/unknown fixture ids/non-empty unsafe destination use;
- large-scaling fixture meets declared minimum file/symbol count;
- evaluator accepts only its stdin payload, returns a boolean independent verdict plus optional regression/hidden-test verdicts, and detects evaluator/test tampering where applicable.

### Step 2 — Observe RED

Focused tests fail only because fixture/evaluator APIs and catalog are absent.

### Step 3 — GREEN implementation

Use deterministic stdlib generation. No network. No hidden oracle file is written into the task repository.

### Step 4 — GREEN verification

Focused tests + full regression.

## Task 3 — Strong-Evidence Adapter in Existing Schema-3 Harness

**Files:**
- Modify: `benchmarks/agent_ab_harness.py`
- Modify: `tests/test_alpha9_benchmark_harness.py`
- Create: `tests/test_benchmark_strong_harness.py`

### Compatibility surface

Legacy invocation remains valid:

```text
--suite ... --baseline-cmd ... --habitat-cmd ... --repetitions 2 --out ...
```

It must continue to produce schema 3 and the existing `runs`, `comparability`, `paired_summary`, and claim-boundary fields expected by historical tests.

### New strong-evidence controls

Add an explicit opt-in mode (exact CLI spelling locked by RED tests) requiring:
- model identity;
- scaffold identity;
- evaluator identity + evaluator command;
- environment fingerprint;
- at least three repetition seeds;
- typed benchmark class/task/revision/fingerprint metadata;
- optional repeated Habitat ablation declarations mapping exactly to `AblationConfig`.

Ablations MUST execute with `--habitat-cmd`, never an alternate command. Planned run metadata is passed through explicit `HABITAT_AB_*` environment/payload fields: condition id, repetition, seed, planned run identity, and serialized ablation.

### Strong execution flow

For each task:
1. materialize exactly one mutation-bound source snapshot for the repetition;
2. construct `BenchmarkSpec` and `ExperimentPlan`;
3. execute `ExperimentPlan.planned_runs()` in its deterministic order;
4. clone/copy the same repetition snapshot independently for each condition;
5. invoke baseline command for filesystem; the same Habitat command for Habitat ON/ablations;
6. invoke independent evaluator with evaluator-only payload;
7. map authoritative observations to `BenchmarkMetrics`, leaving absent values `None`;
8. create `BenchmarkRun`, `EvaluationResult`, `BenchmarkResult`, `RecordedBenchmarkResult`;
9. call `admit_experiment_results`; fail closed if any receipt/control is inconsistent;
10. serialize raw receipts plus `compare_conditions` outputs for filesystem↔Habitat and Habitat↔each ablation.

### Strong report

Keep top-level legacy schema 3 stable. Add a nested, versioned `benchmark_lab` section only when strong mode is enabled. It must include:
- plan identity/conditions/seeds;
- raw recorded receipts and evaluator outputs;
- exact missing planned identities/completeness;
- pair-level comparisons (no aggregate superiority statement);
- separate ingest/warm/task costs;
- class coverage and suite identity;
- strong-evidence admission status and explicit reasons when not admissible.

Legacy `paired_summary` may remain for compatibility, but it must not be the authority for strong evidence and must not coerce missing strong metrics into zero.

### Step 1 — RED tests

Require:
- old two-repetition schema-3 test remains green;
- strong mode rejects <3 repetitions, missing evaluator, missing model/scaffold/evaluator/environment identities;
- same mutation snapshot across conditions in one repetition;
- Habitat ON and all ablations invoke the same Habitat command;
- exact planned run identity/condition/seed/ablation reaches agent payload/environment;
- evaluator-only fields never reach agent payload;
- a fake but deterministic agent/evaluator can produce a complete admitted experiment;
- tampered environment/seed/model/scaffold/evaluator/ablation receipt is rejected;
- absent optional metrics serialize as null, explicit zero stays zero;
- strong section contains raw per-pair deltas and no mean/superiority field;
- one-time ingest and warm reconcile remain distinct from task wall time.

### Step 2 — Observe RED

Full test suite should fail only on the newly required strong mode behavior while legacy schema-3 tests stay green.

### Step 3 — GREEN implementation

Adapt the existing runner. Do not create another executable runner.

### Step 4 — GREEN verification

Focused legacy + strong harness tests, then full suite.
